*Append-only ADR log. Newest last. Numbered. Superseding a decision means adding

## ADR-001: Static client, vanilla HTML/CSS/JS, no framework

- **Status:** accepted (2025, restated 2026-10-09)
- **Deciders:** operator
- **Related:** `ARCHITECTURE.md`, ROADMAP Stage 0

### Context
The core experience (flashcards + SRS) is small and entirely client-side; the
intent is to deploy by pushing a folder to a static host and to run from
`file://`.

### Decision
SQWease ships as static HTML pages with vanilla JS modules and no build step at
runtime. No React/Vue/Svelte, no bundler, no npm runtime dependencies.

### Alternatives
- **React/Vite** — rejected: adds a build pipeline and dependency surface for a
  UI this small.
- **Svelte** — rejected: same, plus compiler complexity.

### Consequences
Fast load, trivial deploy, easy for a stranger to open and run. Cost: manual DOM
work and some copy-paste across pages, addressed by shared `assets/` rather than
a framework.

## ADR-002: Data is authored in `content/`, generated by Node builders, and the output is committed

- **Status:** accepted (2026-02)
- **Related:** `scripts/build-*.js`, `PROJECT_CONTEXT.md` §6

### Context
Decks and Boxes data must be editable by a human, reviewable in diffs, and
loadable from `file://` without a server or fetch.

### Decision
Human-editable sources live in `content/` (CSV/JSON/TSV/MD). Node builders
produce committed JS data files (`flashcards-vocab.js`, `boxes-data.js`,
`content/common-kanji.js`, `data/<lang>/vocab.js`). Generated files are never
hand-edited and are regenerated on change.

### Alternatives
- **Runtime `fetch()` of JSON** — rejected: breaks `file://` (see ADR-010).
- **Query at request time** — rejected: there is no server.

### Consequences
Diffs show both source and output; provenance is clear. Cost: two-step edits and
a risk of stale artifacts (mitigated by `scripts/check.js` presence checks and
T-062).

## ADR-003: Tickets and specs are local markdown files in the repo

- **Status:** accepted (2026-10-09)
- **Deciders:** operator
- **Related:** `tickets/`, `docs/specs/`, T-* tickets

### Context
The project needs a backlog and lightweight specs without committing to a hosted
tracker or creating public issues by accident.

### Decision
Tickets are one markdown file per item under `tickets/` (frontmatter: id,
severity, priority, type, area, related/blocks) with an `INDEX.md`. Specs live
under `docs/specs/`. Both are version-controlled with the code.

### Alternatives
- **GitHub Issues** — deferred: creates ~77 issues on the real repo; can be
  mirrored later from the local files.
- **One big file** — rejected: loses per-item ids and cross-references.

### Consequences
Fully offline, reviewable, and diffable; no native blocking-link UI. Migration to
a hosted tracker is a mechanical import if wanted.

## ADR-004: Work happens on local branches; pushes/PRs are a deliberate later step

- **Status:** accepted (2026-10-09)
- **Deciders:** operator

### Context
A large multi-branch effort (UI overhaul + four languages) was executed in one
session.

### Decision
Create and commit branches locally (`main`, `ui/intl-a11y-perf`,
`lang/spanish|french|korean|mandarin`). Do not push or open PRs automatically; the
operator reviews and pushes.

### Consequences
No unintended public history. The operator owns the merge order. Branch naming
and dependency order are recorded in `ROADMAP.md`.

## ADR-005: Spaced repetition uses a simplified SM-2 with four ratings

- **Status:** accepted (2026-02)
- **Related:** `srs.js`, T-009

### Context
Anki-style scheduling is the core retention mechanism; a full SM-2+Anki clone is
more than the MVP needs.

### Decision
`srs.js` implements new/learning/review states, four ratings (Again/Hard/Good/
Easy), learning steps `[1, 10]` minutes, a graduating interval of 1 day, and a
clamped ease factor (min 1.3).

### Alternatives
- **Full Anki scheduler** — rejected: complex, not needed for the MVP.
- **Leitner boxes only** — rejected: weaker interval model.

### Consequences
Simple and testable; intervals can grow unbounded today (T-009). Constants are
hardcoded and should be tunable later.

## ADR-006: Coloring is romaji-first; Boxes rules live in one module

- **Status:** accepted (2026-09, supersedes the scattered-rules approach)
- **Related:** `syllable-color.js`, `boxes-coloring.js`, T-005, T-006, T-020, T-034

### Context
Coloring repeatedly broke because rules lived in multiple places (`romaji.js`,
`syllable-color.js`, `boxes.html`), and EN alignment drifted.

### Decision
Color is derived **only** from the first syllable of romaji; JA and EN inherit
the aligned color. Generic behavior lives in `syllable-color.js`; all
Boxes-specific rules live in `boxes-coloring.js`. `romaji.js` answers only "is
this a grammatical particle?".

### Alternatives
- **Color from EN** — rejected: English is not the source of truth.
- **Keep adding to shared lists** — rejected: this caused the recurring bugs.

### Consequences
A single owner per concern; residual misalignment remains possible (T-005/T-006)
and is the honest weak point. Palette contrast and distinct dark variants were
added on the UI branch (T-020/T-034).

## ADR-007: Multi-language is a shared deck contract plus a script-injection loader; language branches add only data

- **Status:** accepted (2026-10-09)
- **Related:** `docs/specs/SPEC-language-scaffolding.md`, `assets/vocab.js`, `assets/langs.js`

### Context
Mandarin, Spanish, French, and Korean decks must land without four branches
conflicting on the same core files.

### Decision
Every deck is a module at `data/<code>/vocab.js` that calls
`SqweaseVocab.provide(code, { lang, version, generatedAt, words })` with stable
ids. `SqweaseLangs` declares target-language metadata and capabilities. Language
branches add `content/<code>/` + `data/<code>/` only (plus at most one
`langs.js` line). The loader injects the active deck's script at runtime so
`file://` still works.

### Alternatives
- **Separate pages per language** — rejected: duplicates every page and conflicts.
- **One mega data file edited by all branches** — rejected: guaranteed conflicts.

### Consequences
Clean merges; capability gating handles Japanese-only activities. Cost: deck
modules are loaded dynamically, so a missing file needs a graceful message (it
has one).

## ADR-008: UI strings come from a small string table, not an i18n framework

- **Status:** accepted (2026-10-09)
- **Related:** `assets/i18n.js`, T-045, `docs/specs/SPEC-ui-intl-a11y-perf.md`

### Context
The UI is hardcoded English; multiple UI locales were requested.

### Decision
A ~70-key table for `en/ja/es/fr/ko/zh` with `data-i18n` / `data-i18n-attr`
markup and a `t(key, vars)` function. No external i18n library.

### Alternatives
- **i18next / FormatJS** — rejected: a dependency for a handful of strings.
- **Server-side i18n** — impossible (no server).

### Consequences
Tiny and dependency-free; non-English strings still need native review
(follow-up ticket).

## ADR-009: WCAG 2.2 AA for the primary flow is a requirement, not a nice-to-have

- **Status:** accepted (2026-10-09)
- **Related:** T-032…T-044, palette fix in `syllable-color.js`

### Context
Primary controls were mouse-only divs; the color palette failed contrast.

### Decision
Real semantic controls, keyboard operability, visible focus, `role="status"` for
dynamic regions, `prefers-reduced-motion`, safe-area insets, and a
contrast-compliant light+dark palette are release requirements for the primary
flow. Verified with Lighthouse accessibility (target: no failures).

### Consequences
The UI branch reaches 1.0/zero failures on all six pages. A non-color cue for the
coloring alignment remains open (T-034).

## ADR-010: Keep `file://` support; core data is not fetched

- **Status:** accepted (2026-10-09)
- **Related:** ADR-002, ADR-007, T-055

### Context
Users are told they can open `index.html` directly. Moving to `fetch()` for data
would silently break that.

### Decision
Core decks and libs load as `<script>` (static or injected), never `fetch()`.
Performance work uses `defer` and lazy initialization instead.

### Alternatives
- **`fetch()` + JSON** — rejected: fails under `file://` due to CORS.
- **Embed everything inline** — rejected: blocks first paint.

### Consequences
Offline/`file://` keeps working; large data modules must be deferred and
memoized to stay fast (T-055/T-056).
